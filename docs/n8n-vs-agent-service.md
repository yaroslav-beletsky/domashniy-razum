# n8n vs agent-service: инженерная справка

Вопрос: поднять n8n в домашней сети, собрать workflow и «настроить агента с
инструментами прямо там» — вместо нашего `agent-service`.

Справка честная: под нашу задачу (голосовая колонка, бюджет ответа ~6 с,
лимит навыка Яндекс Диалогов ~4.5 с, несколько колонок, управление из панели).
Фактура по нашему контуру — из `docs/agent-architecture.md`, `agent-service/README.md`
и `panel/README.md`; по n8n — из его штатных возможностей. Код не трогаем.

## Короткий ответ

n8n — это **оркестратор/интегратор**. Наш `agent-service` — **голосовой шлюз с
сущностями `агент / колонка / ключ / MCP`**. Пересекаются они частично: n8n хорошо
закрывает «инструменты и автоматизации», но плохо — жёсткий голосовой data-plane
на хвосте 4.5–6 с. Вывод: **не заменять, а сцепить** — `agent-service` остаётся
голосовым фасадом для `quasar-bridge`, n8n становится **бэкендом инструментов**
(MCP-сервер / HTTP-тул) и расписаний. Полный переезд возможен, но переписывает
панель и теряет десяток мелочей ради гибкости, которая в голосовом режиме почти
не видна.

## Сравнение по нашей задаче

| Критерий | agent-service (сейчас) | n8n (если въехать) |
|---|---|---|
| Роль | OpenAI-совместимый шлюз: мост думает, что это LLM | Workflow-движок с триггерами и нодами |
| OpenAI-совместимость `POST /v1/chat/completions` | Есть, из коробки, стрим | Нужен webhook + Respond-to-Webhook; форма ответа подгоняется руками |
| Стрим (SSE) для моста | Есть (`chatStream`, аккумуляция tool_calls) | У webhook отвечать стримом трудоёмко; обычно отдаём готовый JSON |
| Латентность ответа | Тонкий fas: полный ответ агента ~6 с, накладные `overhead_ms` измеряются | Накладные на исполнение workflow (старт нод, БД, expression-eval) + память нод; на хвосте 4.5 с рискованно |
| Гарантия «успел к 4.5 с» | Жёсткий `budget_ms`, таймаут вызова, финальный вызов без tools, заглушка | Нет «бюджета ответа»: таймаут ноды есть, а сквозного дедлайна с фолбэком — нет |
| Tool-loop | Свой: ≤3 раунда, параллельно, дедуп `(tool,args)`, компрессия вывода, `tool_choice:"none"` в конце | AI Agent-нода делает свой цикл (agent + tools), параметры и поведение — как у LangChain, не наши |
| Инструменты | MCP-клиент (http/sse/stdio), реестр, health, circuit breaker | Огромная библиотека готовых нод + MCP client **и** MCP server; HTTP Request как «тул» |
| Память диалога | Из запроса моста (≤6 пар, TTL 300 с) + SQLite-сессия | Memory-ноды (window/Redis/Postgres) — гибко, но вне формата моста |
| Сущность «агент» | Да: slug, промпт, модель/фолбэк, tools_enabled, max_rounds, budget | Нет. «Агент» — это отдельный workflow; промежуточные слои/теги надо вводить самому |
| Сущность «колонка» и ключ | Да: `stations`, `sk-station-*`, HMAC, привязка колонка→агент | Нет. Ключ = n8n API-key вебхука; разнос по колонкам и их пары — на нас |
| Чипы промпта (`{{time}}/{{station_name}}/{{room}}`) | Есть, по данным колонки | Нужно вычислить из входного JSON и подставить в ноде |
| Голосовая чистка под TTS | Есть: суффикс «коротко, 2–3 фразы», режем markdown/`thinking`, ~600 симв. по границе предложения | Нет. Либо промптом (не гарантия), либо Code-нодой — писать самим |
| Мультиколоночность | Один процесс, маршрут по ключу станции; аудит на колонку/агента | Один workflow = один сценарий; размножение колонок = дисциплина тегов/ветвлений вручную |
| Управление из нашей панели | Прямой Admin API `/admin/*` (CRUD, `If-Match`, SSE-тест) | Панель → **n8n API** (вторично, есть auth/квоты публичного API); у нас — переписать клиент панели |
| Наблюдаемость / аудит | `audit` в SQLite, `overhead_ms`, SSE-тест агента | Executions, лог по нодам, ретраи; удобнее для дебага workflow, но наш аудит-формат другой |
| Секреты | `mcp.env` 0600, в БД только имена | Credentials n8n — своё шифрованное хранилище; отдельный слой |
| Расписания/триггеры | Нет (только запрос-ответ) | Cron, cron/webhook/webhook-форма, очереди, subworkflow — сильно лучше |
| Бэкап/перенос конфигурации | SQLite + `mcp.env` | Экспорт workflow JSON, версии — удобно, но окружение/креды переносятся отдельно |
| Песочница stdio-инструментов | Docker `run --rm --read-only --cap-drop ALL`, allowlist образов | Запуск команд/Code-ноды внутри контейнера n8n; изоляция слабее по умолчанию |
| Эксплуатация | Один узел, `restart: unless-stopped`, health | Ещё один сервис + Postgres (или SQLite) + отдельные креды, обновления, режим execution/queue |

Итог по таблице: n8n выигрывает там, где нужно **много интеграций, расписания,
ретраи и визуальный дебаг**. `agent-service` выигрывает там, где нужен
**предсказуемый голосовой хвост, OpenAI-совместимость, сущности колонка/агент/ключ
и управление нашей панелью**.

## Где n8n реально силён (и чего у нас нет)

1. Готовые интеграции на сотни сервисов — Calendar, почта, Notion, HA, HTTP, БД, Telegram. Нам не надо писать MCP-обёртки под каждую мелочь.
2. AI Agent-нода со своим tool-loop, памятью и подключением LLM/MCP — «агент с инструментами» собирается мышкой.
3. MCP client **и** MCP server: n8n может и потреблять MCP, и сам публиковать MCP-эндпоинт.
4. Триггеры: cron, webhook, очередь, subworkflow, ручной запуск — всё, чего у нашего шлюза нет.
5. Executions/логи/ретраи — визуальный дебаг workflow лучше, чем наши логи.
6. Экспорт/импорт workflow JSON — конфигурация переносима и версионируема.

## Где n8n слаб именно под нас

1. **Латентность.** Голос живёт на хвосте 4.5–6 с. У n8n нет понятия «бюджет ответа с дедлайном и финальным фолбэком» — есть таймауты нод. Накладные на исполнение workflow (старт, БД, expression-eval, память нод) съедают запас. На быстром пути (без инструментов) нам важен тонкий fas, а не движок.
2. **Нет OpenAI-формы и стрима «как надо».** Мост ждёт `POST /v1/chat/completions` со стримом и историей в запросе. У n8n это webhook + Respond-to-Webhook, форма подгоняется, SSE трудоёмок.
3. **Нет сущностей «агент/колонка/ключ».** Ключ `sk-station-*`, привязка колонка→агент, чипы промпта, аудит по колонке — всё это в n8n придётся смоделировать (теги, Folders, отдельные workflow, внешняя БД).
4. **Панель управляет `agent-service` напрямую** по Admin API с `If-Match`/SSE-тестом. С n8n панель придётся переучить на n8n API, а часть операций (выпуск ключа колонки, привязка) ляжет на нас.
5. **Голосовая чистка под TTS** — наша фича (суффикс + обрезка markdown/`thinking`). В n8n это Code-нода или дисциплина промпта, без гарантий.
6. **Очередь и режим execution.** Чтобы не терять голосовые запросы при всплеске, n8n надо поднимать в queue-mode с Redis + воркерами — это уже серьёзнее, чем наш один контейнер.
7. **Мультиколоночность.** Один workflow = один сценарий; разные колонки/агенты — маршрутизация по входу, теги и копии. У нас это одна таблица и один код.

## Вердикт

- **Оставить `agent-service` голосовым шлюзом.** Именно он торчит в `quasar-bridge` как `/v1` и держит малый хвост ответа.
- **n8n — не замена, а сателлит: бэкенд инструментов и автоматизаций.** Публикует свои действия как MCP-сервер и/или HTTP-эндпоинты, которые `agent-service` цепляет как обычные MCP-серверы.
- Панель не трогаем. Ничего в голосовой цепочке не меняется — только добавляются `mcp_servers`, ведущие в n8n.

Это даёт максимум интеграций при сохранении предсказуемой латентности: LLM-цикл и голос остаются у нас, «руки» — в n8n.

## Схема интеграции

```
  Колонка (quasar-bridge)
        │  POST /v1/chat/completions (модель agent:<slug>)
        ▼
  ┌──────────────────────┐        OpenAI-совместимый
  │   agent-service:4100  │◄──── панель: Admin API /admin/* (CRUD, тест SSE)
  │  prompt+чипы+voiceClean│
  │  tool-loop ≤3, budget │
  └───────┬───────────────┘
          │ 1) LiteLLM (модель/фолбэк)
          ▼
   LiteLLM :4000 · домашние модели
          │
          │ 2) MCP-инструменты (registry/pool)
          │    http | sse | stdio
          ▼
  ┌──────────────────────┐      ┌─────────────────────────┐
  │  MCP-серверы «руки»   │      │  n8n (сателлит)          │
  │  hass, builtin, …     │◄────►│  • MCP client/server     │
  └──────────────────────┘      │  • HTTP-тулы для агента  │
                                 │  • cron / webhook / HA   │
                                 │  • интеграции и ретраи   │
                                 └───────────┬─────────────┘
                                             │
                    внутренние системы ──────┘
                    (календарь, почта, HA, БД, уведомления)
```

Порядок сцепки:

1. Поднять n8n в сети `home` (отдельный контейнер + БД, свои креды n8n).
2. Собрать в n8n один-два workflow-«тула» (напр. «создать напоминание», «включить сцену»).
3. Отдать их наружу одним из двух способов:
   - **предпочтительно** — как MCP-сервер (n8n умеет), и добавить его в `agent-service` через `POST /admin/mcp` (`transport: http/sse`, секрет в `mcp.env`);
   - либо как HTTP-эндпоинты с HMAC/`Bearer`, обёрнутые в MCP-ноду n8n.
4. В агенте колонки включить нужные инструменты (`tools_enabled`), проверить `POST /admin/agents/:id/test` (SSE `tool_call`) и тайминг ≤4.5 с.
5. Ограничения на n8n-стороне: короткие таймауты нод, никаких тяжёлых цепочек в голосовом пути, тяжёлое — асинхронно (webhook-вход + cron-продолжение).

## Полный переезд (если очень захочется)

Сжато. Цель: мост и панель ходят вместо `agent-service` в n8n.

- **Этап 0. Решение моста.** OpenAI-совместимый webhook в n8n: принять `messages`, достать историю, вернуть ответ (стрим — по возможности, иначе JSON). Модель/промпт/чипы — из входного JSON.
- **Этап 1. Сущности.** Ввести в n8n модель «агент / колонка / ключ»: Folders или теги + workflow на агента; ключи — n8n API-keys или внешняя БД; привязка колонка→агент — отдельный маршрутизатор по секрету вебхука.
- **Этап 2. Tool-loop и голос.** Заменить наш `runner` на AI Agent-ноду + tools; дописать Code-ноду голосовой чистки (суффикс, обрезка markdown/`thinking`, лимит символов) — иначе TTS захлебнётся.
- **Этап 3. Бюджет.** Реализовать сквозной дедлайн с фолбэком и заглушкой: таймауты нод + `try/catch` + фолбэк-workflow. Это главный риск — воспроизвести наш `budget_ms` точно.
- **Этап 4. Панель → n8n API.** Переписать клиент `/api/agents*`, `/api/mcp*` панели на n8n Public API: создать/включить/выключить workflow, прошить промпт/модель. Часть операций (выпуск ключа колонки, аудит) — поверх n8n или своей БД.
- **Этап 5. Эксплуатация.** n8n в queue-mode (Redis + воркеры), чтобы не терять голос на всплесках; бэкап workflow JSON; обновления n8n как отдельный риск-фактор.

**Что переписывается:** webhook-фасад, tool-loop → AI Agent, голосовая чистка, бюджет/фолбэк, вся админ-часть панели, аудит, выпуск/ротация ключей колонок.

**Риски:** латентность на хвосте 4.5 с; точность воспроизведения `budget_ms` + фолбэка; сущности колонка/ключ вне n8n; панель привязана к n8n API версии; ещё один тяжёлый сервис с БД и очередью в эксплуатации.

**Оправдан, когда:** интеграций становится много и нужны **расписания/триггеры** как первоклассные (события дома сами запускают агента, а не только «спроси колонку»), и появляется выделенный ресурс сопровождать n8n (версии, креды, queue-mode). Если же основной сценарий — «сказал колонке → получил ответ ≤6 с», переезд даёт мало и часто стоит дороже, чем боль `agent-service`.
